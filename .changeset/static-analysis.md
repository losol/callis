Add static analysis. `analyze(expression, options?)` returns the diagnostics of an expression without compiling it: the errors `compile()` throws, with a span and a stable `semantic/…` code, plus warnings, and a syntax error as a diagnostic. `compile()` and `evaluate()` now run the same analysis first and throw `FhirPathSemanticError` with every diagnostic attached when it finds an error. New at compile time: an input or argument of a type a function never accepts (`'a'.abs()`, `skip('1')`, `toString()` on a complex value) is `semantic/type-mismatch` instead of an evaluation error; `$total` outside `aggregate()` is `semantic/undefined-variable`. New warnings: an operator whose operands it never accepts (`1 + 'a'`, which still raises `eval/type-mismatch` when evaluated), a type that does not resolve in `is`, `as` or `ofType()` (`semantic/unknown-type`, still `eval/unknown-type` when evaluated), and `semantic/fraction-ignored` when date/time arithmetic ignores part of a quantity written in the expression (`@2020-01-01 + 1.5 days` adds one day, as FHIRPath 3.0.0 says), which never changes the result. A `Diagnostic` may carry a `hint`.

The `strict` compile option (N1 §11) makes the analyzer reject, as errors, a value that may repeat where an operator or function takes a single item (`(1 | 2) < 3`), equality between a single item and a collection, a value that is not a Boolean where one is expected (`iif('x', 1, 2)`), the operator warnings above, and `first()`, `last()`, `tail()`, `skip()`, `take()` or the indexer on `children()` or `descendants()`, whose order is undefined (`semantic/unordered-collection`). Without a model, analysis knows the types of literals, operators and functions, not of the input's elements; the model-aware checks (an unknown element, a choice element written with its type suffix, a leading type name that does not match the input) run inside the engine and reach the public API with the `model` option later.
